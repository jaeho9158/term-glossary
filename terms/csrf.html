    사이트 간 요청 위조 (CSRF)

    컴퓨터과학·AI
    한 줄 정의: 사용자가 어떤 사이트에 로그인되어 있는 상태를 악용해, 공격자가 그 사용자도 모르게 사용자 권한으로 원치 않는 요청(비밀번호 변경, 송금 등)을 서버에 대신 보내게 만드는 공격입니다.

    쉽게 풀면

    은행 홈페이지에 로그인한 채로 다른 탭에서 수상한 사이트를 열었다고 해봅시다. 그 사이트 안에는 겉으로 보이지 않는 "은행 계좌에서 100만 원을 이체하라"는 요청이 숨겨져 있고, 내 브라우저는 이미 은행에 로그인되어 있으니 이 요청에 로그인 정보(쿠키)를 자동으로 실어서 은행 서버로 보내버립니다. 은행 서버 입장에서는 정상적으로 로그인한 사용자가 보낸 요청처럼 보이기 때문에 그대로 처리해버릴 수 있습니다. 즉 공격자는 사용자의 브라우저를 "대신 심부름 시키는" 방식으로, 사용자가 눈치채지 못하는 사이에 사용자 권한을 도용하는 것입니다.

    왜 중요한가

    CSRF는 인증 자체가 뚫린 것이 아니라 이미 인증된 상태를 악용한다는 점에서, 웹 보안 연구에서 인증(authentication)과 인가(authorization)를 별개로 다루어야 할 이유를 보여주는 대표적인 사례로 다뤄집니다. 전자상거래, 뱅킹, 관리자 콘솔처럼 상태를 변경하는 요청이 많은 서비스일수록 피해가 커질 수 있어, 방어 기법 논문뿐 아니라 웹 프레임워크 설계, API 보안 정책 연구에서도 반복적으로 언급됩니다. 최근에는 SameSite 쿠키 속성처럼 브라우저 차원의 방어와 서버 측 토큰 검증을 함께 다루는 연구도 늘고 있습니다.

    논문에서는 이렇게 쓰입니다

    "제안된 토큰 기반 검증 기법은 위조된 요청의 92% 이상을 서버 단에서 차단하여 CSRF 공격에 대한 방어력을 입증하였다."

    이 문장은 서버가 매 요청마다 정당한 사용자만 알 수 있는 임의의 토큰값을 함께 확인하도록 하여, 공격자가 만든 위조 요청은 이 토큰이 없어 걸러진다는 방어 기법의 성능을 실험으로 검증했다는 뜻입니다. 웹 애플리케이션 보안을 다루는 논문에서 자주 등장하는 방어 대상 공격입니다.

    "본 연구는 SameSite 쿠키 속성 적용이 CSRF 공격 표면을 얼마나 줄이는지 다양한 브라우저 환경에서 비교 분석하였다."

    서버 측 토큰 검증과는 별개로, 브라우저가 제공하는 쿠키 정책 자체를 이용해 CSRF를 막는 접근을 다루는 문장입니다. 브라우저 보안 메커니즘과 웹 애플리케이션 방어를 함께 평가하는 연구에서 흔히 볼 수 있습니다.

    "IoT 기기의 웹 관리 인터페이스를 대상으로 한 실험에서 다수의 제품이 CSRF 방어 수단을 전혀 구현하지 않은 것으로 나타났다."

    전통적인 웹 서비스뿐 아니라 사물인터넷 기기의 임베디드 웹 인터페이스에서도 CSRF 취약점이 흔히 발견된다는 점을 지적하는 문장으로, 보안 취약점 실태조사 연구에서 자주 쓰이는 서술 방식입니다.

    조금 더 깊게 보면

    가장 널리 쓰이는 방어 기법은 서버가 매 세션 또는 매 요청마다 예측 불가능한 값을 발급하고, 요청에 이 값이 함께 실려 오는지 확인하는 방식으로, 흔히 CSRF 토큰 또는 synchronizer token pattern이라고 부릅니다. 이와 별개로 브라우저 차원에서는 쿠키에 SameSite 속성(Strict, Lax, None)을 지정해 다른 사이트에서 발생한 요청에는 쿠키 자체가 자동으로 실리지 않도록 제한하는 방식도 함께 쓰입니다. 또한 서버가 요청의 Origin이나 Referer 헤더를 확인해 요청이 정당한 출처에서 왔는지 검증하는 보조적인 방법도 논문에서 함께 다뤄지는 경우가 많습니다.

    주의할 점

    CSRF는 사용자의 "로그인 상태(신뢰 관계)"를 악용해 대신 요청을 보내게 만드는 공격인 반면, 크로스사이트 스크립팅(XSS)은 악성 스크립트 코드 자체를 사이트에 심어 직접 실행시키는 공격이라는 점에서 다릅니다. CSRF는 공격자가 피해자의 브라우저 안에서 실행되는 코드를 몰래 넣을 필요 없이, 그저 이미 로그인된 상태를 이용하는 것만으로 공격이 성립한다는 점이 특징입니다.
