    버퍼 오버플로우 (Buffer Overflow)

    컴퓨터과학·AI

    ✓ 출처 대조 2026-11-08

    한 줄 정의: 프로그램이 미리 정해둔 메모리 공간(버퍼)보다 더 많은 데이터를 집어넣어 옆 메모리 영역까지 덮어써버리는 현상 또는 이를 악용한 보안 취약점이다.

    쉽게 풀면

    컵에 물을 따르는 상황을 생각해보자. 컵의 용량은 정해져 있는데 그보다 많은 물을 부으면 물이 넘쳐서 옆에 있는 다른 물건까지 젖게 된다. 프로그램의 "버퍼"도 이런 컵과 같다. 예를 들어 이름을 저장할 공간을 10글자로 잡아뒀는데, 사용자가 20글자를 입력하면 나머지 10글자가 원래 다른 데이터나 실행 코드가 있던 메모리 영역을 덮어쓸 수 있다. 공격자는 이 원리를 악용해서 넘치는 데이터 자리에 악성 코드를 몰래 심어 실행시키기도 하는데, 이것이 버퍼 오버플로우 공격이다.

    왜 중요한가

    버퍼 오버플로우는 소프트웨어 보안 분야에서 가장 오래되고 근본적인 취약점 유형 중 하나로, 원격 코드 실행이나 권한 상승 같은 심각한 공격으로 이어질 수 있어 시스템 보안 연구에서 꾸준히 다뤄진다. 그래서 이를 탐지하는 정적·동적 분석 기법, 취약점을 자동으로 찾아내는 퍼징(fuzzing) 기법, 메모리 안전성을 보장하는 프로그래밍 언어와 런타임 방어 기법 연구가 모두 이 개념과 맞닿아 있다. 임베디드 시스템이나 운영체제 커널처럼 성능 때문에 여전히 C/C++을 쓰는 영역에서는 지금도 실무적으로 중요한 문제로 남아 있다.

    핵심 정리

    • 버퍼 오버플로우는 버퍼에 쓰는 데이터가 경계 검사 부족으로 버퍼 바깥, 곧 인접한 메모리 주소의 값까지 훼손하는 현상이다. 대상 버퍼보다 큰 데이터를 경계 확인 없이 복사할 때 생긴다.
    • C와 C++는 배열에 쓰는 데이터가 경계 안인지 자동으로 검사하지 않고, 메모리를 직접 다루게 해 준다. 이 때문에 이 언어들과 전통적으로 연결된다. Java, Python, Eiffel처럼 형식이 엄격하고 메모리 직접 접근을 허용하지 않는 언어는 대부분의 경우 이 문제를 막는다.
    • 문서로 확인되는 가장 이른 악의적 악용은 1988년 모리스 웜의 전파 수단 가운데 하나였다.
    • 방어는 한 겹이 아니라 여러 겹으로 설계한다. 경계 검사를 해 주는 라이브러리·언어, 반환 주소 앞의 값을 검사하는 스택 카나리, 주소를 무작위로 배치하는 ASLR, 데이터 영역의 실행을 막는 DEP/NX가 대표적이다. ASLR은 악용을 어렵게 만들 뿐 불가능하게 하지는 않는다.
    • 연구 문헌에서는 메모리 오류를 오래된 보안 과제로 다룬다. Szekeres 등(2013, 2014)의 논문 제목이 ‘메모리를 둘러싼 끝없는 전쟁’(Eternal war in memory)이고, Shacham 등(2004)은 주소 공간 무작위화의 효과(effectiveness)를 논문 주제로 삼았다.

    예시로 보기

    방어하는 일한계(논문에서 같이 언급되는 점)
    경계 검사·메모리 안전 언어범위를 벗어난 접근을 막거나 오류로 처리해당 언어·라이브러리를 써야 효과가 있음
    스택 카나리함수 종료 때 심어 둔 값이 바뀌었는지 검사주로 스택 버퍼 오버플로우를 탐지
    ASLR주소를 실행마다 무작위로 배치악용을 어렵게 할 뿐 불가능하게 하지는 않음
    DEP/NX데이터 영역을 실행 불가로 표시데이터 영역에 심어 둔 코드의 실행을 차단

    위 표는 개념 비교용 요약이다. 취약점 탐지 연구는 정적 분석(실행 없이 코드 검사)과 퍼징(입력을 바꿔 가며 실행)을 서로 보완하는 접근으로 다루는 경우가 많다.

    자주 하는 오해

    오해바로잡기
    Java나 Python에는 버퍼 오버플로우가 없다.형식이 엄격하고 메모리 직접 접근을 허용하지 않는 언어는 버퍼 오버플로우를 ‘대부분의 경우’ 막는다고 설명된다. ‘전혀 없다’고 쓰면 과장이다.
    ASLR이나 카나리가 있으면 안전하다.이런 방어는 악용을 어렵게 만드는 것이지 취약점을 없애는 것이 아니다. 근본 해결은 경계를 지키는 코드 작성과 검사이다.
    SQL 인젝션과 같은 종류의 공격이다.둘 다 입력값 처리 부실에서 오지만, 버퍼 오버플로우는 데이터베이스가 아니라 프로세스 메모리의 경계를 침범하는 문제이다.
    오래된 취약점이라 이제는 연구할 것이 없다.1988년의 악용 사례 이후에도 Szekeres 등의 2013·2014년 논문처럼 메모리 오류를 다루는 연구가 이어졌다.

    조금 더 깊게 보면

    버퍼 오버플로우는 넘치는 위치에 따라 흔히 스택 오버플로우와 힙 오버플로우로 구분되며, 특히 스택 위에서 함수의 반환 주소를 덮어써 공격자가 원하는 코드를 실행시키는 방식이 고전적으로 많이 연구되었다. 이를 막기 위한 방어 기법으로는 스택에 임의의 값(카나리)을 심어두고 함수 종료 시 값이 바뀌었는지 확인하는 스택 카나리, 메모리 주소를 매번 무작위로 배치해 공격을 어렵게 만드는 주소 공간 배치 난수화(ASLR), 데이터 영역을 실행 불가능하게 만드는 실행 방지(DEP/NX) 등이 논문에서 자주 함께 언급된다. 취약점 탐지 논문을 읽을 때는 정적 분석과 동적 분석(퍼징)이 서로 다른 장단점을 가진 상호보완적 접근이라는 점을 함께 알아두면 도움이 된다.

    주의할 점

    버퍼 오버플로우는 C, C++처럼 메모리를 직접 다루는 저수준 언어에서 특히 흔하며, Java나 Python처럼 메모리 경계를 자동으로 검사하는 언어에서는 상대적으로 드물다. SQL 인젝션처럼 입력값 검증이 부실할 때 발생한다는 공통점이 있지만, 버퍼 오버플로우는 데이터베이스가 아니라 메모리 공간 자체를 침범한다는 점에서 다르다.

    헷갈리기 쉬운 용어

    취약점 이름과 방어 기법 이름이 한 논문에 같이 나오므로 구분해 두면 편하다.
