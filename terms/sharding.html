    샤딩 (Sharding)

    컴퓨터과학·AI
    한 줄 정의: 하나의 큰 데이터베이스를 여러 개의 작은 조각(샤드)으로 나누어 여러 서버에 분산 저장하는 기법입니다.

    쉽게 풀면

    수백만 명의 전화번호가 담긴 두꺼운 전화번호부 한 권을 상상해보세요. 이 한 권을 통째로 들고 다니며 찾기는 힘드니, 이름의 첫 글자를 기준으로 "가~다", "라~바" 식으로 여러 권으로 나누어 서로 다른 책장에 꽂아 둔다고 해봅시다.

    이렇게 하면 각 책장은 전체가 아니라 일부만 담당하므로 찾기도 빠르고, 여러 사람이 동시에 다른 책장에서 찾아도 서로 방해가 되지 않습니다. 샤딩은 데이터베이스에서 이와 똑같은 일을 합니다.

    데이터를 특정 기준(예: 사용자 ID)으로 나누어 여러 서버(샤드)에 분산시킴으로써, 한 서버에 모든 데이터와 요청이 몰리지 않도록 하는 것입니다.

    왜 중요한가

    단일 서버가 처리할 수 있는 데이터 양과 요청 수에는 물리적 한계가 있기 때문에, 사용자 수가 급격히 늘어나는 대규모 서비스에서는 수직적 확장(더 좋은 서버로 교체)만으로는 한계에 부딪히게 됩니다. 샤딩은 데이터를 여러 서버에 나누어 수평적으로 확장할 수 있게 해주는 핵심 기법이기 때문에, 분산 시스템·데이터베이스 논문에서 확장성(scalability) 문제를 다룰 때 빠지지 않고 등장하며, 최근에는 블록체인의 처리량 개선을 위한 방법으로도 활발히 연구됩니다.

    어떤 절차인가

    샤딩은 하나의 논리적 데이터 집합을 샤드 키를 기준으로 나누어 여러 서버(샤드)에 분산 저장하는 수평 분할 기법입니다. 일반적인 절차는 다음과 같습니다.

    1. 데이터와 질의 패턴을 보고 샤드 키(예: 사용자 ID)를 정합니다.
    2. 키를 샤드에 대응시키는 규칙을 정합니다. 해시 기반(키의 해시값을 샤드 수로 나눈 나머지 등), 범위 기반(키의 구간별), 목록(디렉터리) 기반이 대표적입니다.
    3. 요청이 오면 샤드 키로 담당 샤드를 찾아 해당 서버로 보냅니다.
    4. 데이터가 늘면 샤드를 추가하고 일부 데이터를 옮기는 재분배(리샤딩)를 합니다.

    가상의 예(코드로 계산): 키 10,000개(user:0 ~ user:9999)를 FNV-1a 해시로 샤드 4개에 배치하면 샤드당 2,500개로 고르게 나뉩니다. 한편 쓰기가 최신 ID에 몰리는 서비스에서 최근 1,000건을 ID 구간(0~2499, 2500~4999, …)으로 나누면 1,000건이 모두 마지막 샤드에 쌓이지만, 해시 기반에서는 4개 샤드에 250건씩 퍼집니다. 이 차이가 범위 기반의 핫스팟 위험입니다. 해시의 나머지 방식으로 샤드를 4개에서 5개로 늘리면 키의 약 80.1%(10,000개 중 8,006개)가 다른 샤드로 이동합니다. 일관성 해싱(링)에서는 새 샤드가 맡게 되는 키만 옮기면 되므로 이동 비율이 이상적으로 1/5 = 20% 수준으로 줄어듭니다(실제 값은 가상 노드 수와 해시 함수에 따라 달라집니다).

    언제 쓰고 무엇을 얻나

    • 언제 쓰나: 한 서버로 데이터량이나 요청량을 감당하기 어려울 때 읽기·쓰기 용량을 서버 수에 따라 늘리기 위해 씁니다(수평 확장). 복제와 달리 서버마다 서로 다른 데이터를 갖습니다.
    • 얻는 것: 저장 용량과 처리량의 확장, 부하 분산, 지역별 배치를 통한 응답 지연 감소.
    • 치르는 비용: 여러 샤드에 걸친 조회·조인·트랜잭션이 복잡해지고, 샤드 키를 잘못 고르면 핫스팟이 생기며, 리샤딩 시 데이터 이동이 큽니다. 일반적으로 샤딩만으로 가용성이 높아지지는 않고 복제와 함께 설계합니다.
    • 블록체인 분야의 샤딩: 네트워크를 여러 샤드로 나누어 각 샤드가 거래의 일부만 검증하도록 해 처리량을 높이려는 설계입니다(예: Luu 등, 2016). 이때는 데이터 저장뿐 아니라 합의와 보안 가정이 함께 쟁점입니다.

    논문에는 이렇게 적는다

    • 샤드 키 선택 근거와 분할 방식(해시/범위/디렉터리), 샤드 수, 리샤딩 전략(일관성 해싱 등)을 적습니다.
    • 데이터 분포(샤드별 건수와 크기), 부하 분포(샤드별 요청 수)와 편향 지표를 보입니다.
    • 처리량, 지연시간(평균과 꼬리 지연), 샤드 수에 따른 확장성 곡선을 실험으로 제시하고, 교차 샤드 질의 비율을 함께 보고합니다.
    • 복제 수준, 일관성 모델, 장애 시나리오를 명시합니다.

    논문에서는 이렇게 쓰입니다

    예시 문장

    아래는 용어의 쓰임을 보여 주려고 만든 예시로, 실제 논문에서 가져온 문장이 아닙니다.

    "대규모 사용자 데이터를 사용자 ID의 해시값을 기준으로 샤딩(sharding)하여 16개 노드에 분산 저장함으로써 단일 노드의 처리 부하를 낮췄다."

    이 문장은 데이터를 특정 규칙에 따라 여러 서버로 쪼개 저장함으로써, 하나의 서버가 모든 요청을 처리하느라 과부하되는 문제를 줄였다는 뜻입니다.

    "제안된 블록체인 프로토콜은 네트워크를 여러 샤드로 나누어 각 샤드가 트랜잭션의 일부만 검증하도록 함으로써 전체 처리량을 크게 향상시켰다."

    블록체인 분야에서 모든 노드가 모든 거래를 검증해야 하는 병목을 샤딩으로 해소하려는 연구 사례로, 데이터베이스뿐 아니라 분산 합의 시스템에도 같은 원리가 적용됨을 보여줍니다.

    "지리적으로 분산된 사용자 기반을 고려하여 지역 기준 샤딩 전략을 적용한 결과, 사용자와 가까운 샤드에서 요청을 처리하여 평균 응답 지연시간이 감소하였다."

    샤드를 나누는 기준을 ID 해시가 아니라 지리적 위치로 삼은 사례로, 샤딩 기준을 어떻게 설계하느냐에 따라 얻을 수 있는 이점이 달라진다는 점을 보여줍니다.

    조금 더 깊게 보면

    샤딩을 설계할 때 핵심은 어떤 값을 기준으로 데이터를 나눌지 정하는 샤드 키(shard key)의 선택입니다. 해시 기반 샤딩은 데이터를 고르게 분산시키기 쉽지만 특정 범위의 데이터를 한 번에 조회하기 어렵고, 범위 기반 샤딩은 범위 조회는 쉽지만 특정 구간에 데이터가 몰리는 핫스팟이 생기기 쉽습니다.

    또한 샤드 수를 늘리거나 줄이는 리샤딩(재분배) 과정에서 데이터 이동이 대규모로 발생할 수 있어, 이를 최소화하기 위한 일관 해싱(consistent hashing) 같은 기법이 함께 다뤄지는 경우가 많습니다.

    주의할 점

    샤딩 기준(샤드 키)을 잘못 정하면 특정 샤드에만 데이터와 요청이 몰리는 "핫스팟(hot partition)" 문제가 생길 수 있어, 로드밸런싱과 함께 설계해야 효과가 있습니다. 또한 여러 샤드에 걸친 데이터를 한 번에 조회하거나 수정하는 작업은 단일 서버일 때보다 복잡해진다는 점도 고려해야 합니다.

    헷갈리기 쉬운 용어

    분산 시스템에서 비슷한 말로 섞이는 용어입니다.

    용어무엇을 하나데이터 구성
    샤딩데이터를 나눠 여러 서버에 분산 저장서버마다 서로 다른 일부 데이터
    복제(replication)같은 데이터를 여러 서버에 복사서버마다 같은 데이터(가용성·읽기 확장)
    로드밸런싱요청을 여러 서버에 분배데이터 분할과는 별개의 개념
    일관성 해싱샤드 수가 바뀔 때 이동하는 데이터를 최소화하는 배치 규칙샤딩 방식의 한 구현

    참고 문헌

    1. Kleppmann, M. (2017). Designing Data-Intensive Applications. O'Reilly Media.
    2. Karger, D., Lehman, E., Leighton, T., Panigrahy, R., Levine, M., & Lewin, D. (1997). Consistent hashing and random trees: Distributed caching protocols for relieving hot spots on the World Wide Web. Proceedings of the 29th Annual ACM Symposium on Theory of Computing, 654–663.
    3. Luu, L., Narayanan, V., Zheng, C., Baweja, K., Gilbert, S., & Saxena, P. (2016). A secure sharding protocol for open blockchains. Proceedings of the ACM SIGSAC Conference on Computer and Communications Security, 17–30.
